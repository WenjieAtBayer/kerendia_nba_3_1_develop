# RX Feature QC & EDA — Independent Recomputation Validation

This skill generates a QC notebook that independently recomputes RX feature values from
raw source data for a stratified sample of HCPs, then compares them side-by-side against
the feature notebooks' output Delta tables. It validates that the pipeline code computes
what it claims to compute.

**Companion skill:** [rx-overall-skill](../rx-overall-skill/SKILL.md) generates the feature
notebooks being validated. This skill's "After Modifying — How to Verify" section points
here for deeper validation after any pipeline change.

**Column sanitization note:** First occurrence and frequency features use different column
sanitization rules (first occurrence: lowercase, "/" to "_"; frequency: uppercase, "/" to " OR ").
The QC template applies the matching rules for each feature type.

## When to Read This Skill

Read this skill when the user wants to:
- Validate feature outputs after running the rx-overall-skill notebooks
- Spot-check whether specific feature values are correct
- Debug a suspected feature computation bug
- Verify a pipeline modification didn't break existing features

5. Recency QC (all 6 sub-features)
6. Frequency Claim Count QC
7. Frequency Lag QC
8. Frequency Change QC
9. Patient Counts QC + Summary + Known-discrepancy self-test

## Stratified Sampling Design

The QC samples 5-6 HCPs from the HCP universe using **volume-based stratified sampling**:

1. Count total claims per PROVIDER_ID in the raw RX data within the cohort lookback window
2. Rank HCPs by claim count, divide into tertiles (high / medium / low volume)
3. Sample 2 from high, 2 from medium, 1-2 from low tertile
4. Default seed: `42` (reproducible). User can override the seed or pin specific PROVIDER_IDs.

**Why stratified:** Heavy-tail features like skewness, lag window sums, and type x window
counts behave differently for high-volume vs low-volume HCPs. Sampling only low-volume
HCPs would miss bugs that only manifest with large claim counts.

## Data Provenance

The QC notebook reads from the same pre-processed Delta tables as the feature notebooks:

| Input | Config Variable | Contents | Pre-processing |
| --- | --- | --- | --- |
| Total events input | `rx1_file_path` | All RX claims (702M rows) | Extracted from Snowflake IQVIA, NPI mapped to PROVIDER_ID, product names mapped to PRODUCT_GROUP, date standardized to SVC_DT |
| 12M claims input | `rx_freq_file_path` | 12M-filtered RX claims (193M rows) | Same as above, additionally filtered to 12-month window |

**Both inputs are pre-processed** — they are NOT raw Snowflake extracts. The upstream
pipeline (02_Input_Data_Creation) has already:
- Mapped NPI_ID to PROVIDER_ID
- Applied the market basket product group mapping (PRODUCT_GROUP)
- Standardized the date column to SVC_DT
- Filtered to the HCP universe

The QC validates feature engineering logic (rx1/rx_freq -> feature outputs), NOT data
extraction/mapping logic (Snowflake -> rx1/rx_freq).

## Floating-Point Comparison Strategy

| Feature Type | Comparison | Rationale |
| --- | --- | --- |
| First occurrence (max EVENT_TIME) | Exact integer equality | datediff returns int |
| Recency min event time | Exact integer equality | min of integers |
| Recency counts (all sub-types) | Exact integer equality | count / countDistinct return int |
| Recency skewness | abs(m - n) < 1e-4 | Same F.skewness() function, but Spark partition ordering can cause float-level differences |
| Frequency claim counts | Exact integer equality | count returns int |
| Frequency lag | Exact integer equality | sum of integers over window |
| Change in frequency | abs(m - n) < 1e-4 | Division in formula produces floats |
| Patient counts | Exact integer equality | countDistinct returns int |

Tolerance rationale: 1e-4 is loose enough to avoid false positives from distributed
float arithmetic, but tight enough that real bugs produce deltas orders of magnitude larger.

## What the QC Can Catch

- Wrong aggregation (e.g., sum instead of max for first occurrence)
- Wrong filter (e.g., missing EVENT_TIME >= 0, wrong 12M window bounds)
- Wrong column mapping (e.g., using GENERIC_NAME instead of PRODUCT_GROUP)
- Wrong column sanitization (e.g., missing paren removal in frequency)
- Wrong formula (e.g., change frequency denominator)
- Wrong time window flag logic (e.g., days_diff < w vs days_diff <= w)
- Wrong dedup logic for patient counts
- Batch processing bugs (if a batch boundary splits an HCP's data)

## What the QC Cannot Catch

- **Bugs upstream of rx1_file_path** — Snowflake extraction, NPI-to-PROVIDER_ID mapping,
  product group mapping, HCP universe filtering. The QC reads pre-processed Delta, not
  raw Snowflake. Bugs in the upstream 02_Input_Data_Creation pipeline are invisible.
- **Semantic correctness of feature definitions** — e.g., is max(EVENT_TIME) the right way
  to measure "first occurrence"? That is a design question, not a code bug.
- **Bugs that only manifest outside the sample** — 5-6 HCPs cannot cover every edge case.
  Increasing the sample size or pinning specific HCPs can mitigate this.
- **EVENT_TYPE assignment bugs** — the Recency QC hardcodes `lit("rx")` for EVENT_TYPE,
  matching what DataFrameMerger does for RX claims. If DataFrameMerger has a bug in how it
  assigns event types (e.g., miscategorizing some RX claims as DX), this QC will not catch
  it because both manual and notebook paths use "rx". Acceptable for an RX-only skill, but
  worth noting when extending to DX/PX.
- **Helper class internal bugs that don't affect output values** — e.g., memory management,
  caching, intermediate column naming.
- **Timestamp/timezone issues** in SVC_DT parsing (if upstream date standardization has bugs).

## Known-Discrepancy Self-Test

The QC notebook includes a self-test cell (last cell before summary) that:
1. Takes one HCP_COHORT_ID from the sample
2. Creates a copy of the notebook output with one feature value intentionally corrupted
3. Re-runs the comparison against this corrupted output
4. Confirms the mismatch is detected with the correct delta

This ensures the QC itself is working — a QC that only ever reports "all passed" is
indistinguishable from one that doesn't check anything.

6. If mismatches are found, investigate using the raw claims display cells.
